01 / DOCUMENT MODEL

Transform the request,
not a collection.

A Flow operates on one evolving document. Steps can validate fields, derive values, transform lists inside the payload, and assign Outputs.

Connections establish order and routing. Explicit input and output mappings are used when crossing an asset or data boundary, rather than between every pair of steps.

Mongo-style syntax. In-memory execution.

The intended runtime is a Java parser/executor. A live MongoDB database is not required. MongoDB 6.0 is the reference for the explicitly supported operator subset, not a promise of full compatibility.

Studio owns the authoring experience

Typed contracts, visual definitions, configuration feedback, and schema-aware field pickers help authors compose valid steps. Calculation authoring includes Visual and Advanced JSON modes.

Operator names, argument types, and supported signatures come from a versioned catalog interface. Frontend checks assist authors; they are not authoritative execution validation.

The backend owns runtime semantics

The backend must resolve trusted schemas, validate asset references, build the internal representation, and compile the executable pipeline. Preview and execution must use the same semantics.

External operations require an explicit runtime boundary. They must not be presented as native aggregation stages.

03 / REUSE WITH EXPLICIT BOUNDARIES

Reuse the decision.
Keep the contract.

Each asset owns its Inputs, Outputs, and versions. Calling one from a Flow is an explicit mapping—not a shared global contract.

01

Pin a published version

Select a Decision Table or Decision Tree and its version. Editing another draft does not silently change the referenced publication.

02

Map inputs and results

Bind the called asset’s Inputs from the Flow. Select its entire output or a nested object, then assign matching fields into a declared object Variable.

03

Define failure behavior

Lookup configuration includes stop-on-missing or continue-with-null behavior. The backend must enforce contracts and return structured execution errors.

Planned reusable Flow execution boundaries +

Reusable Flow calls are specified as synchronous, pinned-version calls. Child Inputs and Outputs require validation. Child failures propagate to the parent; calls share a deadline and have a nesting-depth limit. Direct and indirect recursion are prohibited, and traces must preserve parent-child correlation. These are architecture requirements, not implemented runtime capabilities.

Success has an output payload

The response envelope includes success: true, data, and an optional trace. The selected published version supplies the contract and definition.

Failure carries structured errors

A failure returns success: false and errors, without a successful data payload. Errors may identify the affected step, rule, or field.
